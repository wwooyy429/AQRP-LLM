# 部署源码协议：严格原始身份与显式末尾 LF 规范

本候选仅修复部署协议及其离线软件边界。原回测 `3e68866a46ca88ff16481c31b3c2c822` 的实际终态仍为 Runtime Error，权威账本仍为 failed；该失败不能由新的规范追溯改写。原始证据见 `audit/review_packages/gates-20261028/lean/delivered_failure_result.json`。

## 为什么需要版本化

原 worker 首个被拒文件为 `engineering_smoke.py`。冻结文件的严格规范哈希与 worker 观测哈希不同；仅在冻结副本末尾追加一个 LF，可同时复现观测哈希及全部受控格式计数。当前项目的声明源码读回一致。具体发生差异的平台步骤、其他 worker 文件和旧任务的原因仍未证明。

旧协议已经接受 UTF-8 BOM 与通用换行符解码规范，但保留末尾 LF 数量。直接改变这个旧哈希函数会改变历史任务的含义。本候选保留旧协议，另由 `config/deployment.json` 显式选择新清单。

## 两个清单格式

v1 是 `{"path.py": "source_sha256"}`，继续严格保留末尾 LF，并继续使用原失败诊断。旧输入、部署哈希、任务身份、回执及 failed 结论不升级。

v2 是闭集对象：

```json
{
  "schema_version": 2,
  "source_identity_policy": "utf8_sig_universal_newlines_terminal_lf_v1",
  "files": {
    "path.py": {
      "source_sha256": "原有 UTF-8-sig/通用换行解码后、保留 EOF 的 SHA-256",
      "canonical_sha256": "仅将末尾 LF 连续段替换为一个 LF 后的 SHA-256",
      "terminal_lf_count": 1
    }
  }
}
```

整个 v2 对象进入部署哈希，再进入计划、完整配置与原始 admission；禁止解包后只冻结 `files` 或其中一个哈希。构建产物的 `source_files` 继续提供原严格哈希索引，新消费者优先选择完整 `deployment_manifest`。无显式部署配置的历史构建夹具保留 v1。

## 校验边界

- 本地冻结、首次生成输入、扣额前校验及 PROJECT 源码读回均要求原始严格身份相符。即使只有 EOF 差异，也必须重新构建和冻结，不能用 worker 策略放行本地改动。
- 只有原 admission 明确包含 v2 时，worker 才可接受末尾 LF 数量差异。它同时核对规范哈希，并用观测正文和声明的 LF 数重建原严格哈希；不能直接复制清单预期值作为计算结果。
- 规范只改终端 LF 连续段。正文空白、行内及行尾空格、注释、导入、字符串、因子公式、额外语句均留在哈希中。
- 原字节、通用换行字节和规范字节必须都是有效 UTF-8 Python，且 AST 相同；只编译与解析，不执行。编码 cookie 不一致、显式续行导致语法差异、无效 UTF-8、NUL 等均拒绝，并只报告固定错误文字。
- v2 每源文件最多 2 MiB、末尾 LF 为 0–64、最多 512 个文件；路径须安全，拒绝大小写别名、文件与祖先路径冲突及生成输入。所有路径先校验，再读取源码；符号链接不能逃逸源码根。
- `_engineering_task_input.py` 与 `_collection_task_input.py` 不进入 v2 实现清单，输入本身仍由独立哈希固定。
- v2 成功报告增加闭集聚合证据，绑定原部署哈希和文件数，记录 EOF 规范化文件数及原身份是否相符。它不能声称发生规范化时仍具有原始字节相等性，也不构成平台签名或数据认证。
- Research、LEAN、采集任务的报告解析与结算核对原 admission。历史恢复不读取当前生成清单，不为旧任务补造新协议。

## 验证及上线限制
